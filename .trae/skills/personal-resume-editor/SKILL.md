# Personal Resume Editor

## Purpose

将用户提供的旧简历、补充事实、修改文字和目标 JD 整理为可信的 HTML/CSS 简历，并通过 Chromium 导出经过校验的 PDF。

本 Skill 自带：

- 标准 A4 紧凑模板，支持单页、双页和三页以上多页形式。
- `assets/logos/` 中的 102 个本地 SVG Logo 库。
- 公司品牌注册表与 SVG 主色提取工具。
- PDF、DOCX、HTML、Markdown 和纯文本简历的文本抽取工具。
- HTML 溢出检查、Logo/品牌色检查和 PDF 文字层检查。
- `references/xyz-resume-standard.md` 中的 Harvard / Google XYZ / r/EngineeringResumes 内容与 ATS 质量规范。

## Privacy And Package Boundaries

- 本 Skill 分发包只包含通用规范、脚本、模板、字体、Logo 和测试，不包含任何真实简历、个人照片、联系方式、PDF、预览图或修改记录。
- `output/` 和 `working/` 是运行时目录。分发或归档 Skill 时只能保留其中的 `.gitkeep`，不得连同用户数据一起复制。
- 不得从工作区的简历交付目录、历史输出目录或下载目录批量复制文件到 Skill 包。
- 用户输入只在当前工作副本内处理；需要制作可分享 Skill 时，必须重新执行姓名、邮箱、电话、学校、个人账号和绝对路径扫描。

## Non-Negotiable Rules

1. 不得编造学历、公司、岗位、日期、奖项、指标、项目职责或技术实现。
2. 润色可以改善措辞、结构和重点，但不得改变事实含义。
3. 用户没有提供量化结果时，不得自行补充百分比、金额、规模或排名。
4. 原始简历和用户修改说明必须保留为只读输入；生成内容写入新的 `output/<version>/`。
5. 正式 PDF 必须使用本 Skill 的 `scripts/export-pdf.mjs`，不得交付浏览器“打印/另存为 PDF”的结果。
6. 正式简历只允许引用本地图片。公司 Logo 必须是 SVG，不得热链。
7. 每段公司经历必须使用该公司 Logo 的主色作为 Banner 左边框，并使用对应浅色作为 Banner 背景。
8. 页首默认只显示姓名，不显示推断出的求职岗位；仅当原简历明确包含求职岗位，或用户明确要求添加时，才显示岗位。
9. 姓名必须是页首最显著的文字；默认模板使用 32px，不得为了塞入岗位而缩小姓名。
10. 默认不展示每周出勤天数、可实习时长、到岗日期等信息。只有用户明确要求写入，并同时提供具体信息时才展示；不得仅凭原简历或文件名自动添加。
11. 个人照片是可选项。用户提供替换照片时必须使用其提供的新照片，不得继续沿用旧照片。
12. 每次修改完成后，必须在返回结果中先给出简短但重要的修改建议，再用表格逐项列出所有文字润色、删减、补充、重排和版式调整，不得只概括为“已优化”。
13. 正文内容默认使用纵向、全宽、逐项排列，不把多个经历、技能或校园条目并排放在多栏中；仅标题与日期、公司与岗位、姓名与照片等元数据允许左右对齐。

## Resolve The Skill Directory

所有命令均以包含本文件的目录作为 `SKILL_DIR`：

```bash
SKILL_DIR="<path-to-this-skill>"
cd "$SKILL_DIR"
```

不要假设用户旧简历位于 Skill 目录中。

## Step 1: Intake Existing Material

接受以下任意组合：

- 旧简历：PDF、DOC、DOCX、RTF、HTML、Markdown 或 TXT。
- 用户已经写好的替换文字或补充材料。
- 目标岗位、JD、语言、目标公司和强调方向。
- 用户上传的公司 SVG Logo。
- 用户上传的个人简历照片，以及明确的保留、替换或删除照片要求。

对于文件型旧简历，先抽取文本：

```bash
./scripts/extract-resume.sh "/absolute/path/old-resume.pdf" "working/source-resume.txt"
```

将以下内容整理到 `working/facts.md`：

- `Verified facts`：旧简历和用户明确提供的事实。
- `Requested changes`：用户要求替换、删除、补充或强调的内容。
- `Open questions`：确实影响真实性、且无法从材料中判断的问题。

复制 `templates/change-log.md` 为 `working/change-log.md`，并从第一次编辑开始逐项记录变更，不要等 PDF 完成后再凭记忆补写。

缺少非关键内容时使用明确的 `[待补充]` 草稿标记；正式导出前必须解决或删除这些标记。

这是个人简历工作流。不得保留模板演示内容、虚构公司、示例联系方式、彩蛋或与用户无关的项目。

## Step 2: Decide Page Mode Before Generation

生成 HTML 前必须完成页数决策：

- 用户指定单页：使用 `single`。
- 用户指定双页：使用 `double`。
- 用户指定三页及以上：使用 `multi`，并确定页数。
- 用户没有说明：明确告知“未指定页数，将默认生成紧凑单页”，然后直接使用 `single`，不要因此阻塞任务。

初始化独立工作副本：

```bash
npm run init -- --name <version-name> --mode single
npm run init -- --name <version-name> --mode double
npm run init -- --name <version-name> --mode multi --pages 3
```

只编辑新建的 `output/<version-name>/index.html` 和同目录 `styles.css`。

### Target Variant Policy

- 用户要求岗位方向版本时，从同一份事实基线派生，教育、实习、联系方式和事实指标保持一致，只调整与岗位相关的经历选择、顺序和技能呈现。
- 教育背景、实习经历、联系方式等共享模块默认必须在所有岗位版本中保持一致；用户修改共享模块时同步更新全部现有版本，除非用户明确要求某个版本采用不同内容。
- 用户指定主版本后，主版本是共享模块的唯一内容与排版来源；先修改主版本，再将共享模块的 HTML 和 CSS 完整同步到其他分支。
- 导出前必须同时验证共享模块的文字、字号、行距、间距、换行位置、元素高度和占行数一致；不能只做文本对比。
- 同时生成游戏公司版与常规版时，文件名使用 `<姓名>-修改后简历-vN（游戏公司）.pdf` 和 `<姓名>-修改后简历-vN（常规）.pdf`。
- 游戏公司版可加入用户明确提供的游戏履历、游戏内容影响力、游戏 Demo 与相关校园品牌经历；常规版默认不展示这些岗位特定内容。
- 游戏履历放在“技能及其他”下方，以单列、全宽、逐项方式展示平台、品类、时长、段位、角色养成和 Demo 实践，不虚构游戏理解或策划能力。
- 游戏公司版的辅助项目也保持纵向单列；为控制篇幅，每个次要项目优先压缩为一个逻辑 bullet，不使用左右双栏。

## Step 3: Rewrite Content

开始润色前必须阅读 `references/xyz-resume-standard.md`。

按照“事实校验 → 目标岗位匹配 → 语言润色 → 篇幅压缩”的顺序处理。

- 每条实质性经历 bullet 必须执行 XYZ 审核：明确成果 X、证据 Y、方法 Z。X 与 Z 必须清晰；Y 优先使用用户提供的硬指标，没有硬指标时使用真实的规模、覆盖、频次或复用范围。
- XYZ 的语序不固定，可以写成“通过 Z 完成 X，取得 Y”或“主导 Z，实现 X/Y”；不得为了统一模板牺牲自然中文表达。
- 不得为了补齐 Y 编造数据。缺少结果证据时，保留准确的行动与产出，并在最终建议中明确指出待补充的真实证据。
- Bullet 优先表达：具体动作、业务对象、方法、可验证结果。
- 不要机械地把每段经历拆成 Situation / Task / Action / Result 四段。适合压缩时，使用“背景或任务 + 行动 + 结果”的单句结构；背景已由项目标题或上下文说明时，可直接写“行动 + 结果”。
- 只有在问题背景对理解技术决策、业务价值或个人职责确有必要时才保留背景；不得为了套 STAR 模板增加空泛句子。
- 每条 bullet 聚焦一个主题，优先保留个人主导动作、关键方法和可核验结果；技术体系建设等无法自然量化的内容可以保留行动与产出，不强行补造结果。
- “单句式 STAR”指一个逻辑 bullet，不要求强制占一个视觉行；文字过长时允许自然换行，不得通过极小字号或 `white-space: nowrap` 强行塞入。
- 不要为了节省空间把无关任务合并为一句。只有背景、行动和结果属于同一业务问题时才压缩合并；不同主题仍分别逐条展示。
- 每条 bullet 以 1–2 个视觉行为目标，复杂且高价值内容最多 3 行；超过 3 行时优先拆分或删减低价值背景。
- 优先使用主导、搭建、设计、分析、识别、验证、优化、自动化、标准化、推动、上线等具体动词；避免空泛的“负责”“参与”“协助”，但不得在没有事实依据时把参与改写成主导。
- 同一职位内按相关性和影响力从高到低排序，最强成果放在第一条，满足 5 秒扫描。
- 将 JD 关键词自然映射到真实经历，不要堆砌关键词。
- 优先保留可核验结果、个人职责和关键决策，删除背景废话和同义重复。
- 单页模式优先压缩内容，其次收紧间距；不要先把正文缩到难以阅读。
- 默认保留教育背景、工作/实习经历、项目经历和专业能力。没有对应事实的章节直接删除。
- 联系方式、链接、公司名称、岗位和日期在所有位置保持一致。
- 保持模板的语义化 HTML 结构；确需新增或删除章节时才改变结构。
- 内容编辑放在 HTML，视觉、密度和页面平衡调整集中在 CSS，不要破坏 screen-to-PDF 导出机制。
- 每修改一个字段、标题、摘要或 bullet，立即在 `working/change-log.md` 记录原文、修改后内容、修改类型和原因。
- 删除、合并或重排内容也属于变更，必须记录；不能只记录新增内容。
- 字号、间距、分页、照片、Logo、Banner、章节顺序等视觉或结构变化也必须记录。

### Header Policy

- 默认页首只放姓名、联系方式和必要的个人摘要，姓名使用较大字号。
- 不要根据项目、专业或实习经历自行生成“数据科学家”“算法工程师”等求职岗位。
- 原简历明确写有求职岗位时可以保留。
- 用户要求针对 JD 制作并明确希望展示目标岗位时，可以添加 `<p class="target-role">...</p>`。
- 默认删除每周出勤天数、可实习时长、到岗日期等排期信息，即使原简历正文或文件名中包含这些内容。
- 只有同时满足“用户明确要求在简历中展示”和“用户提供具体排期信息”时，才可在页首添加出勤信息。
- 用户只提供排期但未要求展示，或只要求展示但未提供具体信息时，均不得写入。

### Personal Photo Policy

- 个人照片可保留、替换或删除，以用户要求为准；用户未说明时，原简历有照片则保留，没有则不主动添加。
- 用户提供新照片并要求替换时，将文件复制到当前工作版本的 `assets/images/`，HTML 只引用该本地文件。
- 支持 PNG、JPEG、WebP；不得热链，不得把照片写入最终 PDF 交付目录之外的公开位置。
- 默认只做保持宽高比的居中裁切，不改变面部特征，不用生成式图片替换本人，不擅自美化或修改背景。
- 若用户明确要求修图、换底色或生成证件照，应先确认需求并使用适用的图像能力；完成后仍需用户核对身份呈现。
- 替换后必须在 PDF 截图中检查头像是否清晰、方向正确、比例自然，且没有拉伸、截断面部或遮挡文字。

有照片时可使用：

```html
<header class="profile-header profile-with-photo">
  <div class="profile-copy">...</div>
  <img class="profile-photo" src="./assets/images/profile.png" alt="<姓名>简历照片" />
</header>
```

无照片时保持默认 `.profile-header`，不要放空白头像框或占位图。

## Step 4: Resolve Company Branding

先读取 `assets/brands.json`，使用公司标准名或 aliases 匹配现有品牌。未命中注册表时，必须先按公司中英文名在 `assets/logos/` 的 102 个本地 SVG 中做大小写不敏感匹配；只有本地库也没有时才进入网络搜索。

已注册公司经历必须使用：

```html
<article class="role-card" style="--brand: #3C8CFF; --brand-soft: #EDF3FF">
  <div class="role-banner">
    <img src="../../assets/logos/ByteDance.svg" alt="字节跳动 Logo" />
    ...
  </div>
</article>
```

路径必须根据 `output/<version>/index.html` 保持为 `../../assets/logos/...`。

### Unknown Company

先检查完整本地 Logo 库：

1. 枚举 `assets/logos/*.svg`，按公司中文名、英文名、简称和品牌名匹配文件名。
2. 找到本地 SVG 后，直接使用该文件，并通过 `register-logo.mjs` 将名称、aliases 和主色写入注册表。
3. 本地库未命中时，才由 Agent 主动寻找，不要先把任务退回给用户。

网络补充流程：

1. 搜索公司官方网站、官方品牌中心或官方媒体资料页。
2. 优先下载官方 SVG；其次使用能够明确核验品牌归属的 SVG 图标库。
3. 核对公司全称、图形和品牌色，避免把产品 Logo 当作公司 Logo。
4. 无法找到可信 SVG、下载受限或存在多个无法判断的 Logo 时，再请用户上传 SVG。
5. 不得使用生成式图片模型仿造公司 Logo。

将找到或用户上传的 SVG 注册到本地：

```bash
node scripts/register-logo.mjs \
  --key <company-key> \
  --name "<公司标准名称>" \
  --file "/absolute/path/logo.svg" \
  --aliases "英文名,简称"
```

脚本会复制 SVG、提取主要颜色、生成浅色 Banner 背景并更新 `assets/brands.json`。若自动识别的颜色不符合官方品牌规范，使用 `--color "#RRGGBB"` 覆盖。

## Step 5: Layout Pages Intentionally

- 每个 `.resume-page` 是一张固定 A4 页面。
- 单页只有一个 `.resume-page`，双页必须正好两个，多页必须至少三个。
- 复制或移动完整的 `<section>`、`.role-card` 或 `.project-entry` 分配页面。
- 不要让同一段公司经历或项目在两页之间意外断开。
- 多页简历的每一页都应有明确内容边界和相近的底部留白。
- 实习 bullet、项目 bullet、校园经历、技能、语言和兴趣默认各自占一个全宽逻辑行，按从上到下的顺序排列。
- 禁止使用 CSS `columns: 2`、双栏 Grid 或左右并列卡片承载两条不同内容；此规则同样适用于校园经历和技能列表。
- 允许在同一行内将公司与日期、项目名与日期、学校与 GPA 等关联元数据左右对齐，但正文内容必须保持单列阅读顺序。
- 一条内容超出页面宽度时允许自然折行；不要使用 `white-space: nowrap`、横向缩放或过小字号制造“视觉单行”。
- Banner 必须使用对应公司的 `--brand` 和 `--brand-soft`，Logo 透明直贴，不增加白色底座、白边、额外描边或装饰圆角。
- 不同 SVG 的画布留白不同，应逐枚校准视觉大小；图形视觉高度以 Banner 高度的 75%–80% 为参考，始终保持宽高比，禁止裁切或拉伸。
- 保留本地 PingFang SC 与 EB Garamond 字体组合，不要随意替换成单一全黑体或全衬线字体。

## Step 6: Validate And Export

首次运行：

```bash
npm install
```

先检查 HTML。数字必须与选择的页数一致：

```bash
npm run validate -- "output/<version-name>/index.html" 1
```

再导出 PDF：

```bash
npm run export -- \
  "output/<version-name>/resume.pdf" \
  "output/<version-name>/index.html"
```

最后检查：

```bash
pdfinfo "output/<version-name>/resume.pdf"
pdftotext "output/<version-name>/resume.pdf" -
```

浏览器仅用于 HTML 预览。如果用户通过浏览器打印或另存为 PDF，必须将其视为诊断文件，并重新使用官方导出脚本生成正式 PDF。

验收标准：

- PDF 页数与用户选择一致。
- Chromium 导出器没有报告任何页面内容溢出。
- PDF 包含姓名、主要经历、教育、项目和技能等应有内容。
- 每条核心经历已经完成 XYZ 审核；硬指标、规模或范围均可追溯到用户材料。
- Bullet 以 1–2 行为主、复杂项不超过 3 行；没有只剩 1–4 个字的孤行。
- 不含主观自评、被动职责清单、无实质内容的 buzzword 或无法解释的内部缩写。
- HTML 中不存在 `[待补充]`、模板示例、虚构指标或远程图片。
- 每段公司经历均有正确的本地 SVG、主色边框和浅色背景。
- 除非用户明确要求并提供具体内容，否则简历中不得出现出勤天数、实习时长或到岗日期。
- 用户要求替换照片时，最终 PDF 必须使用新照片，且不再引用旧照片。
- 对最终 PDF 或页面截图执行视觉检查，确认没有文字重叠、裁切、孤行或异常留白。
- 对比 HTML 预览与 PDF 截图，确认 Chromium 的 screen 布局在 PDF 中得到一致复现。
- 检查正文阅读顺序为从上到下的单列结构；不得出现校园经历、技能项或不同 bullet 左右并排的情况。

## Step 7: Return Suggestions And Complete Change Table

每次生成或修改简历后，最终回复必须包含以下三部分，顺序固定：

1. 修改后 PDF 的可点击路径与版本号。
2. `重要修改建议`：给出 2–5 条简短、高价值、可执行的建议。
3. `修改明细`：使用 Markdown 表格逐项说明所有实际修改。

重要建议要求：

- 只写影响投递质量的重要问题，例如缺少可核验指标、职责边界不清、岗位匹配不足、信息仍需确认或篇幅取舍。
- 对未满足 XYZ 的 bullet，明确指出缺失的是成果 X、证据 Y 还是方法 Z，并给出需要用户补充的事实类型。
- 明确区分“本次已修改”和“建议后续补充”，不得让用户误以为建议内容已经写入 PDF。
- 不得建议用户编造指标；缺少数据时建议补充真实证据或保持定性表达。
- 如果没有待补充问题，也必须明确写“当前无必须补充项”，并给出至多 2 条可选优化建议。

修改明细表格式固定为：

```markdown
| 模块/位置 | 原文或原样式 | 修改后 | 修改类型 | 修改原因 |
| --- | --- | --- | --- | --- |
| 实习经历 / 第 1 条 | 原文 | 修改后的完整表述 | 润色 | 强化行动、方法与结果 |
```

表格完整性要求：

- 每一个被修改的个人信息字段、摘要、标题、bullet 和技能项至少占一行。
- 删除内容时，`修改后` 写“已删除”；新增内容时，`原文或原样式` 写“无”。
- 合并多个原始 bullet 时，列出被合并的原文范围，不得只写“合并优化”。
- 章节重排、页数、姓名字号、照片替换、出勤信息处理、Logo、Banner 色、字体和间距调整均要列入表格。
- 纯机械且全局一致的标点或日期格式调整可以合并为一行，但必须说明覆盖范围。
- 表格中的原文与修改后文本必须足以定位具体变化，不得使用“内容优化”“表达调整”等空泛占位词。
- 若基于上一版生成新版本，以用户指定版本或上一版为对比基准；首版以用户原始简历为基准。
- 返回表格前，对照 `working/change-log.md`、最终 HTML 和 PDF 文本进行一次完整性复核。
